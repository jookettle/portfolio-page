지난 글 끝에서 레거시로 쓰던 MongoDB(각주)를 PostgreSQL(각주)로 옮기겠다고 말씀드렸는데요, 이번 시즌에 드디어 그 약속을 지켰어요. 다만 이번 글은 "옮겼습니다, 빨라졌어요" 같은 자랑보다는 옮기는 동안 내린 결정 하나와, 그 결정 때문에 나중에 치른 비용 이야기에 가까워요.

## 왜 옮겼나

마쵸봇의 핵심은 모의 주식이에요. 유저가 돈을 벌고, 잃고, 가끔은 말도 안 되게 많이 벌어요. 문제는 그 "말도 안 되게"였어요. 지갑을 자바스크립트 Number(각주)로 저장하다 보니 일정 금액을 넘으면 정밀도가 깨졌고, 끝까지 가면 Infinity가 돼버렸어요. 급기야 지갑이 무한대가 된 상태를 조건으로 하는 업적("초월")까지 생겼으니 말 다 했죠.

게다가 랭크 모드와 솔로 모드가 따로 돌아가는데, 두 모드의 데이터가 어떤 관계인지가 스키마 어디에도 적혀 있지 않았어요. 코드를 읽어야만 알 수 있는 규칙이 너무 많았어요.

그래서 스키마가 강제되는 PostgreSQL로 옮기고, ORM은 Prisma(각주)를 쓰기로 했어요. 유저 테이블은 하나로 합치고 `isRank` 컬럼으로 모드를 나눴어요. `(userId, isRank)`에 유니크 제약을 걸어서 "한 사람당 모드별로 딱 한 줄"을 DB가 보장해요. 지갑은 기존 Float 옆에 문자열로 된 정확한 값(`walletExact`)을 따로 두고, 계산은 BigInt(각주)로 해요.

## 제일 큰 결정: 코드를 안 고치기로 했어요

마쵸봇 코드에는 `User.findOne(...)`을 부르고, 필드를 고치고, `user.save()`를 부르는 몽구스(각주) 스타일 코드가 28개 파일에 걸쳐 250곳 가까이 박혀 있어요. 이걸 전부 Prisma 호출로 바꾸는 건 사실상 봇을 다시 짜는 일이었어요.

그래서 방향을 반대로 잡았어요. 호출하는 쪽은 그대로 두고, 그 아래에 몽구스처럼 생긴 층을 하나 끼워넣은 거예요. Prisma에서 읽어온 행을 Proxy(각주)로 감싸서, 필드를 바꾸면 그 필드를 "더러워짐(dirty)"으로 표시해두고, `save()`가 불리면 바뀐 필드만 골라서 UPDATE를 날려요.

```ts
return new Proxy(state, {
  get(target, prop) {
    if (prop === "save") return save;
    if (prop === "markModified") return (field: string) => dirty.add(field);
    if (prop === "toObject") return () => JSON.parse(JSON.stringify(target));
    if (prop === "_id" || prop === "id") return target[pkField];
    return target[prop as string];
  },
  set(target, prop, value) {
    const key = prop as string;
    target[key] = value;
    dirty.add(key);
    return true;
  }
}) as any;
```

`$in`, `$gt` 같은 몽고 쿼리 연산자도 Prisma의 `in`, `gt`로 번역해주는 함수를 따로 뒀어요. 덕분에 게임 로직은 한 줄도 안 건드리고 DB만 갈아끼울 수 있었어요. 라이브로 돌아가는 봇을 멈추지 않고 옮기는 데는 이게 제일 현실적인 선택이었다고 지금도 생각해요.

## 그리고 청구서가 날아왔어요

추상화는 공짜가 아니더라고요. 호출하는 쪽에서는 이게 몽구스인지 Prisma인지 안 보이니까, 층이 몽구스와 조금이라도 다르게 굴면 버그가 어디서 왔는지 찾기가 어려웠어요.

**`.id`가 거짓말을 해요.** 위 코드에서 `.id`나 `._id`를 읽으면 그 모델의 기본키(각주)를 돌려줘요. 몽구스 시절 코드가 `doc._id`를 많이 쓰니까 넣은 편의 기능이었어요. 그런데 상점 테이블은 기본키가 `rowId`이고, `id`는 "몇 번 진열칸인지"를 뜻하는 진짜 컬럼이에요. 결국 상점 코드가 `slot.id`로 진열칸 번호를 읽으면 번호 대신 cuid(각주) 문자열이 튀어나왔어요. 코드만 봐선 절대 이상해 보이지 않는 버그였어요. 지금은 `toObject().id`로 원본 값을 꺼내 쓰고 있어요.

**스키마와 DB가 따로 놀아요.** `schema.prisma`에는 `walletExact` 같은 컬럼이 있는데 실제 DB에는 없는 상태가 한동안 이어졌어요. 배포 과정에 마이그레이션(각주) 단계가 없어서, 스키마를 고친 사람이 DDL(각주)을 따로 적용하는 걸 기억해야 했거든요. 이게 시즌 리셋 날 랭킹 조회에서 P2022(컬럼 없음) 에러로 터졌어요.

지금은 컨테이너가 뜰 때 마이그레이션을 먼저 돌리고, 실패하면 봇을 아예 안 띄워요. 스키마가 어긋난 채로 봇이 떠서 잘못된 데이터를 조용히 쓰는 것보다는 안 뜨는 편이 낫다고 판단했어요. 앱 컨테이너와 워커 컨테이너가 동시에 마이그레이션을 잡으면 락만 기다리니까, 워커는 `SKIP_MIGRATIONS=true`로 빠지게 해뒀어요.

## 가장 아팠던 날: 봇이 엉뚱한 DB를 보고 있었어요

마쵸봇 서버에는 DB가 사실상 두 개 있었어요. 하나는 `.env`에 적힌 주소의 DB, 하나는 docker-compose(각주)가 띄우는 Postgres 컨테이너의 볼륨이에요. 그리고 compose 파일에는 `.env`의 주소를 덮어쓰는 `DATABASE_URL` 한 줄이 있었어요.

설정을 정리하면서 이 줄을 "env_file을 덮어쓰니 헷갈리고 위험하다"고 보고 지웠어요. 그런데 알고 보니 그 한 줄이 봇을 진짜 DB로 보내는 유일한 장치였어요. `.env`에 적힌 쪽은 5월에서 멈춘 사본이었고, 실제 서비스는 8월 말까지 compose 볼륨에서 돌고 있었거든요.

증상은 이랬어요. 유저분들한테서 "가입이 안 된 걸로 나와요", "스킨이 없어졌어요" 같은 제보가 들어왔어요. 처음엔 이걸 데이터 버그로 보고 스킨 복구 스크립트까지 짜서 돌렸어요. 5월자 사본을 상대로요. 시즌 리셋도 거기에 한 번 돌렸고요.

방향을 틀게 된 건 문득 떠오른 질문 하나였어요. "얼마 전에 DB 주소 설정을 건드렸는데, 그거 영향 아닐까?" 그때부터는 코드 대신 데이터를 봤어요.

- 제보 스크린샷 날짜와 지금 붙어 있는 DB의 마지막 쓰기 시각을 비교해봤더니, DB 쪽이 몇 달 전에서 멈춰 있었어요.
- 서버에 어떤 컨테이너에도 붙어 있지 않은 242.9MB짜리 도커 볼륨(`machobot_pgdata`)이 남아 있었어요.
- 이 볼륨을 운영 DB에 바로 붙이지 않고, 복제본을 따로 띄워서 먼저 들여다봤어요. 8월 말까지의 기록이 그대로 있었어요.

다행히 진짜 DB는 사고 동안 한 줄도 건드려지지 않았어요. 복구는 이런 순서로 했어요.

1. 진짜 DB를 먼저 통째로 백업했어요. 뭘 하든 되돌릴 수 있는 지점부터 만들어두고 시작했어요.
2. 오버라이드를 지운 PR을 되돌리고, 봇을 다시 진짜 DB에 붙였어요. 사고 동안 사본 쪽에 쌓인 활동은 버리기로 했어요.
3. 진짜 DB에 마이그레이션 기준점(각주)을 잡고 누락된 컬럼을 적용했어요.
4. 시즌 리셋을 진짜 DB에서 다시 돌렸어요. 스페셜 업적 240건은 리셋에서 빼서 그대로 남겼어요.
5. 랭크와 솔로 모드의 스킨 가방을 하나로 합치는 작업(23,891행)을 했고, 그 과정에서 스킨 두 개를 잃은 유저 한 분도 백업을 보고 복구했어요.

지금은 샤드(각주) 8개가 모두 정상이고, 봇은 8,725개 서버에서 랭크 유저 28,081명의 데이터를 제대로 읽고 있어요.

## 재발 방지

사고 이후에 compose 파일 맨 위에 이런 주석을 달아뒀어요.

```yaml
# 봇이 쓰는 DB 는 아래 postgres 서비스(볼륨 machobot_pgdata)다.
#
# .env 의 DATABASE_URL 은 믿으면 안 된다. (...) 아래 environment: 의
# DATABASE_URL 오버라이드가 봇을 진짜 DB 로 보내는 유일한 장치다.
#
# 한 번 이 오버라이드를 "env_file 을 덮어써서 위험하다"고 판단해 지운 적이
# 있는데, 그 순간 봇이 5월자 사본에 붙어 유저들이 미가입으로 취급됐다.
# 지우지 말 것.
```

주석으로 끝낼 일은 아니라서, 운영 DB에 손대기 전에는 반드시 백업을 뜨고, 백업은 git에 안 올라가는 폴더에 날짜별로 쌓고 있어요. 앞에서 말한 마이그레이션 자동 적용도 같은 맥락이에요. "누군가 기억해야 하는 절차"를 하나씩 없애는 방향으로 가고 있어요.

이번에 배운 걸 정리하면 세 가지예요.

1. **위험해 보이는 코드도 이유가 있어서 거기 있을 수 있어요.** 왜 있는지 모르는 줄은 지우기 전에 누가 왜 넣었는지부터 확인해야 해요.
2. **설정 파일이 아니라 데이터를 봐야 해요.** "지금 봇이 어느 DB를 보고 있는가"는 `.env`를 읽어서가 아니라 붙어 있는 DB의 마지막 쓰기 시각을 봐야 알 수 있는 거였어요.
3. **증상을 고치기 전에 최근에 바뀐 것부터 의심해야 해요.** 스킨이 사라졌다는 제보에 복구 스크립트부터 짰는데, 사실 데이터는 멀쩡했고 바뀐 건 봇이 바라보는 곳이었어요. 급할수록 "최근에 뭘 바꿨지?"부터 묻는 게 제일 빠른 길이었어요.

DB를 옮기면서 4년 묵은 코드 곳곳에 숨어 있던 버그도 꽤 찾았어요. 그중에서도 디스코드 버튼을 한 번 더 누르면 같은 보상을 두 번 받을 수 있던 문제와, 거래 상대가 없는 모의 주식 시장이 왜 인플레이션으로 무너질 수밖에 없었는지는 다음 글에서 따로 풀어볼게요. 많은 기대 부탁드려요.
